## Q1: "какие основные возможности агента, какой класс реализует"
Основные возможности агента реализуются через **интерфейс `AIAgentFeature`** и его специализированные варианты (`AIAgentGraphFeature`, `AIAgentFunctionalFeature`). Каждый feature предоставляет конкретную функциональность (например, планирование, обработку инструментов, логирование), которую можно добавить в агента через конвейер (pipeline). 

Ключевые аспекты:
- **`AIAgentFeature`** определяет конфигурацию и ключ для хранения состояния feature.
- **`AIAgentGraphFeature`** и **`AIAgentFunctionalFeature`** специализируются для установки в графический или функциональный конвейер агента соответственно.
- Features управляются через `AgentLifecycleHandlersCollector`, который собирает обработчики событий жизненного цикла, связанных с конкретными feature.

Примеры возможностей, которые могут реализовываться через features:
- Планирование задач (например, `AIAgentPlannerFeature`).
- Работа с инструментами (ToolRegistry).
- Логирование и мониторинг.
- Кастомизация стратегий выполнения.

Таким образом, **модульность и расширяемость агента обеспечиваются именно через механизм features**, каждый из которых инкапсулирует определённую функциональность.

## Q2: "как конфигурируется агент"
На основе предоставленного контекста, агент конфигурируется через **паттерн Builder**, реализованный в классе `AIAgentHelper`. Основные шаги и компоненты конфигурации:

---

### 1. **Создание билдера**
Начинается с вызова статического метода:
```kotlin
val builder = AIAgentHelper.builder()
```

---

### 2. **Задание конфигурации агента (`AIAgentConfig`)**
Конфигурация определяет ядро поведения агента и создаётся через конструктор или билдер. Ключевые параметры:
- **`prompt`** — начальный промпт (сообщения, инструкции).
- **`model`** — модель LLM (например, `OpenAIModels`).
- **`maxAgentIterations`** — лимит итераций (защита от бесконечных циклов).
- **`missingToolsConversionStrategy`** — стратегия обработки отсутствующих инструментов в промпте.
- **`responseProcessor`** (опционально) — постобработка ответов LLM.
- **`serializer`** (опционально) — сериализатор аргументов инструментов (по умолчанию `KotlinxSerializer`).

Пример:
```kotlin
val config = AIAgentConfig(
    prompt = prompt { /* ... */ },
    model = OpenAIModels.Default,
    maxAgentIterations = 10,
    missingToolsConversionStrategy = /* ... */
)
```

---

### 3. **Добавление инструментов (`ToolRegistry`)**
Инструменты регистрируются в `ToolRegistry` и передаются в билдер:
```kotlin
val tools = ToolRegistry {
    // добавление инструментов, например:
    // tool<MyTool>()
}
builder.withTools(tools)
```

---

### 4. **Указание стратегии выполнения (`AIAgentGraphStrategy`)**
Стратегия определяет **логику работы агента** (например, графovina конвейера, планирование). Примеры:
- `GraphAIAgent` — Uses strategy based on a graph of steps.
- `PlannerAIAgent` — Uses a planning-based strategy.
Передаётся в билдер:
```kotlin
builder.withStrategy(myStrategy)
```

---

### 5. **Установка фич (`AIAgentFeature`)**
Дополнительные функциональные модули (например, логирование, кэширование). Фичи настраиваются через:
```kotlin
builder.withFeature(myFeature, featureConfig)
```
Фичи могут требовать собственной конфигурации (`FeatureConfig`).

---

### 6. **Дополнительные параметры**
- **`id`** — уникальный ID агента (если `null`, генерируется UUID).
- **`clock`** — объект времени (по умолчанию системные часы).
- **`installFeatures`** — лямбда для динамической установки фич в контексте выполнения.

---

### 7. **Сборка агента**
После настройки всех компонентов агент создаётся через:
```kotlin
val agent = builder.build(
    inputType = /* TypeToken для Input */,
    outputType = /* TypeToken для Output */,
    promptExecutor = /* PromptExecutor */,
    agentConfig = config
)
```

---

### **Ключевые классы из контекста:**
| Класс | Роль |
|-------|------|
| `AIAgentHelper` | Центральный билдер для создания агентов. |
| `AIAgentConfig` | Конфигурация промпта, модели, лимитов, обработки инструментов. |
| `GraphAIAgent` | Пример агента с graph-стратегией. |
| `AIAgentContext` | Контекст выполнения (доступ к среде, pipeline, хранилищу). |
| `RegisteredFeature` | Установленная фича с её конфигурацией. |

---

### **Итоговый пример:**
```kotlin
val agent = AIAgentHelper.builder()
    .withTools(myToolRegistry)
    .withStrategy(GraphAIAgent.Strategy)
    .withFeature(LoggingFeature, LoggingConfig())
    .build(
        inputType = typeToken<String>(),
        outputType = typeToken<Result>(),
        promptExecutor = myExecutor,
        agentConfig = AIAgentConfig(
            prompt = myPrompt,
            model = myModel,
            maxAgentIterations = 5
        )
    )
```

Конфигурация **декларативна** и разделяет ядро (`AIAgentConfig`), расширения (`ToolRegistry`, `Strategy`, `Features`) и исполнение (`PromptExecutor`).

## Q3: "как агент работает с историей сообщений"
Агент работает с историей сообщений через несколько ключевых механизмов, описанных в контексте:

## 1. **Хранение истории в контексте**
Основная структура — `AgentContextData`, которая содержит:
- `messageHistory: List<Message>` — полная история сообщений текущей сессии
- `lastOutput: JSONElement?` — последний вывод агента (предпочтительный способ, `lastInput` устарел)
- `rollbackStrategy` — стратегия отката состояния, которая может включать историю сообщений

## 2. **Управление историей через фичи**
- **ChatMemory** — фича для персистентного хранения истории между сессиями агента:
  - Позволяет сохранять/загружать историю разговоров
  - Поддерживает окно сообщений (`windowSize(20)`) для ограничения длины
  - Интегрируется через `installChatMemory {}` в конфигурации агента

## 3. **Стратегии сжатия истории**
Для управления размером контекста LLM используются стратегии компрессии:
- **`FromLastNMessages(n)`** — сохраняет последние N сообщений + создаёт TLDR-сводку
- **`FromTimestamp(timestamp)`** — сохраняет сообщения с определённого времени
- **`ChunkedHistoryCompressionStrategy(chunkSize)`** — разбивает историю на чанки и суммирует каждый
- **`WholeHistoryMultipleSystemMessages`** — сохраняет все системные сообщения

Стратегии:
1. Фильтруют исходную историю (оставляют только нужные сообщения)
2. Генерируют сводку (TLDR) о отфильтрованных сообщениях через LLM
3. Собирают финальный промпт: системные сообщения + первое пользовательское + сводки + память

## 4. **Rollback (откат)**
При ошибках или необходимости повтора агент может откатиться:
- `RollbackStrategy.Default` — полный откат контекста включая историю
- `RollbackStrategy.MessageHistoryOnly` — только история сообщений

## Ключевые принципы:
- История хранится в `Message` объектах (роли: user/assistant/system/tool)
- Стратегии сжатия автоматически управляют длиной контекста для LLM
- Системные сообщения и первое сообщение пользователя обычно сохраняются всегда
- Сводки (TLDR) заменяют сжатые части истории, сохраняя контекст

Таким образом, агент гибко управляет историей: сохраняет между сессиями, сжимает для LLM, поддерживает откат и обеспечивает контекстную преемственность.

## Q4: "как реализованы стратегии компактизации контекста"
На основе предоставленного контекста реализации стратегий компактизации контекста в фреймворке **Koog** можно описать следующим образом:

### Основной механизм
Стратегии компактизации реализованы через абстрактный класс **`HistoryCompressionStrategy`**, который определяет метод `compress`. Этот метод принимает:
1. **`llmSession`** — текущую сессию взаимодействия с языковой моделью (типа `AIAgentLLMWriteSession`).
2. **`memoryMessages`** — список сообщений (`Message`) из истории памяти, подлежащих сжатию.

Цель стратегии — уменьшить размер контекста (количества сообщений) при сохранении ключевой информации для корректной работы агента.

### Ключевые элементы реализации
1. **Абстрактная стратегия**:
   - `HistoryCompressionStrategy` является базовым классом, требующим реализации `compress`.
   - Внутри него есть защищённый (`protected`) вспомогательный метод **`compressPromptIntoTLDR`**, который использует сессию `llmSession` для сжатия текущего диалога в краткое резюме («TL;DR»). Это предполагает использование LLM для обобщения истории.

2. **Конкретные стратегии** (перечислены в комментариях к классу):
   - **`WholeHistory`** — вероятно, оставляет историю без изменений (без компактизации).
   - **`FromLastNMessages`** — сохраняет только последние `N` сообщений.
   - **`FromTimestamp`** — фильтрует сообщения по времени (например, сохраняет только сообщения после определённого временного порога).
   - **`Chunked`** — разбивает историю на чанки (например, фиксированного размера) и обрабатывает их отдельно.
   - **`RetrieveFactsFromHistory`** (из `ai.koog.agents.memory.feature.history`) — извлекает из истории ключевые факты или сущности, возможно, с использованием семантического поиска или дополнительной обработки.

3. **Интеграция с контекстом агента**:
   - Стратегии работают в рамках **`AIAgentContext`**, который содержит:
     - `messageHistory` — полная история сообщений.
     - `rollbackStrategy` — стратегию отката состояния (например, `Default` или `MessageHistoryOnly`), которая может влиять на то, как применяется компактизация (например, при восстановлении состояния).
   - При использовании стратегии в процессе выполнения агента, сжатие истории может происходить динамически, чтобы уложиться в ограничения контекста LLM.

### Примерная логика работы
1. Агент накапливает историю сообщений в `AIAgentContext`.
2. При необходимости (например, перед отправкой запроса к LLM) применяется выбранная стратегия `compress`.
3. Стратегия анализирует `memoryMessages` и возвращает сокращённый список, который затем используется для формирования промпта.
4. Если стратегия использует `compressPromptIntoTLDR`, LLM генерирует резюме, которое заменяет часть истории.

### Важно
- Контекст класса `HistoryCompressionStrategy` не включает полную реализацию конкретных стратегий, лишь их названия и общую структуру.
- Другие классы в контексте (например, `AgentContextData`, `ToolCallEventContext`) описывают структуры данных для событий и контекста выполнения, но не относятся напрямую к алгоритмам компактизации.

Таким образом, фреймворк предоставляет гибкий механизм для управления размером контекста через переопределяемые стратегии, что позволяет адаптировать историю сообщений под ограничения LLM и требования задачи.

## Q5: "как реализован tool calling"
На основе предоставленного контекста, реализация **tool calling (вызова инструментов)** в фреймворке Koog построена на следующих ключевых компонентах:

### 1. **Модель данных (DTO)**
*   **`ReceivedToolResult`**: Основной класс, передающий результат вызова инструмента. Содержит:
    *   `tool` — имя инструмента.
    *   `toolArgs` — аргументы вызова (в виде `JSONObject`).
    *   `result` — результат выполнения инструмента (структурированный, `JSONElement`).
    *   `resultKind` — тип результата (успех, ошибка валидации и т.д.).
    *   `content` — строковое представление результата для отображения.
*   **`ToolResult` (устаревший интерфейс)**: Исторический маркерный интерфейс. Сейчас результаты инструментов — это обычные сериализуемые данные (KotlinX Serialization), и расширять `ToolResult` не требуется.

### 2. **Сериязация и преобразование сообщений**
*   **`ToolCallDescriber`**: Интерфейс, преобразующий внутренние сообщения о вызовах инструментов (`Message.Tool.Call`, `Message.Tool.Result`) в другие форматы (например, текстовые описания для LLM, которые не поддерживают нативные tool-call сообщения). Реализация `JSON` сериализует вызовы в JSON-объекты.
*   **`ToolResult` companion `json`**: Преднастроенный экземпляр `kotlinx.serialization.Json` для сериализации результатов.

### 3. **Событийная модель**
*   **`ToolCallStartingEvent`**: Событие, генерируемое **в момент вызова** инструмента. Содержит метаданные: `toolName`, `toolArgs`, `toolCallId`, `runId`. Это позволяет отслеживать начало выполнения.
*   **`EventHandler`**: Фича (feature) агента, позволяющая подписаться на события, включая события инструментов (`onToolCallStarting`, `onToolCallFinished`). Устанавливается в пайплайн агента и предоставляет колбэки для логирования, мониторинга или кастомизации.

### 4. **Поток обработки (высокоуровнево)**
1.  **Агент** принимает решение вызвать инструмент (на основе ответа LLM или логики).
2.  Генерируется и публикуется событие **`ToolCallStartingEvent`**.
3.  Вызывается обработчик инструмента (Environment), который выполняет логику и возвращает объект **`ReceivedToolResult`**.
4.  Результат (`ReceivedToolResult`) преобразуется в сообщение `Message.Tool.Result`.
5.  Если LLM поддерживает tool-call, это сообщение отправляется обратно в контекст. Если нет — используется `ToolCallDescriber` для преобразования в user/assistant сообщение.
6.  Генерируется завершающее событие (например, `ToolCallFinishedEvent`), которое можно перехватить через `EventHandler`.

### Итог
Tool calling реализован как **сериализуемая контрактная модель данных** (`ReceivedToolResult`), **событийная система** для отслеживания жизненного цикла вызовов (`ToolCallStartingEvent`, `EventHandler`) и **гибкий механизм преобразования** сообщений (`ToolCallDescriber`) для совместимости с разными моделями LLM. Это позволяет фреймворку быть независимым от конкретного провайдера LLM и обеспечивает точный учёт и контроль над выполнением инструментов.

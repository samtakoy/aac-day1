## Q1: "какие основные возможности агента, какой класс реализует"
Основные возможности агента реализуются через механизм **фич (features)**, а ключевым классом для этого является интерфейс **`AIAgentFeature`** и его специализированные подтипы.  

### **Основные возможности агента:**
1. **Расширяемость через фичи** — агент строится из независимых модулей (фич), каждая из которых добавляет определённую функциональность (например, работа с инструментами, логирование, планирование и т.д.).
2. **Конфигурация** — каждая фича имеет тип конфигурации `TConfig`, расширяющий `FeatureConfig`, который создаётся через `createInitialConfig` на основе конфигурации агента.
3. **Интеграция с конвейером** — фичи устанавливаются в конкретный тип конвейера агента:
   - `AIAgentGraphFeature` — для графового конвейера (`AIAgentGraphPipeline`).
   - `AIAgentFunctionalFeature` — для функционального конвейера (`AIAgentFunctionalPipeline`).
   - `AIAgentPlannerFeature` — для конвейера планировщика (`AIAgentPlannerPipeline`).
4. **Уникальный ключ** — каждая фича имеет ключ `key` типа `AIAgentStorageKey<TFeatureImpl>`, который используется для хранения и доступа к её реализации в рамках агента.

### **Класс, реализующий возможности:**
- **`AIAgentFeature<TConfig, TFeatureImpl>`** — базовый интерфейс для всех фич. Он определяет:
  - `key` — идентификатор фичи в хранилище агента.
  - `createInitialConfig` — создание конфигурации фичи на основе конфигурации агента.
- **Специализированные интерфейсы** (`AIAgentGraphFeature`, `AIAgentFunctionalFeature`, `AIAgentPlannerFeature`) — добавляют метод `install`, который инсталлирует фичу в соответствующий конвейер и возвращает её реализацию.

Таким образом, **архитектура агента построена на композиции фич**, каждая из которых отвечает за свою часть функциональности и интегрируется через конкретный тип конвейера. Это позволяет гибко настраивать и расширять возможности агента без изменения его ядра.

## Q2: "как конфигурируется агент"
На основе предоставленного контекста фреймворка **Koog** конфигурация агента происходит через **установку и настройку фич (features)**. Вот основные принципы:

### 1. **Типы агентов**
Существует два основных типа агентов:
- **`FunctionalAIAgent`** — для функциональных агентов.
- **`PlannerAIAgent`** — для планирующих агентов.
Оба используют одинаковый механизм фич.

---

### 2. **Основной способ конфигурации: `install`**
Фичи устанавливаются при создании агента (в конструкторе или через билдер) с помощью метода `install`. Каждая фича имеет свой класс конфигурации (наследник `FeatureConfig`), который можно настраивать в лямбде:

**Пример для `FunctionalAIAgent`:**
```kotlin
val agent = FunctionalAIAgent(
    strategy = strategy,
    promptExecutor = promptExecutor,
    toolRegistry = toolRegistry,
    id = "myAgent",
    agentConfig = config,
    clock = clock
) {
    // Установка фичи с настройкой
    install(MyFeature) {
        someProperty = "значение"
        anotherProperty = 42
    }

    // Установка фичи с добавлением обработчика сообщений
    install(TraceFeature) {
        addMessageProcessor(myMessageProcessor)
    }
}
```

**Пример через `AIAgentBuilder`:**
```kotlin
val agent = AIAgentBuilder<Input, Output>()
    .withStrategy(strategy)
    .withPromptExecutor(executor)
    .withToolRegistry(registry)
    .install(MyFeature) {
        property = "value"
    }
    .build()
```

---

### 3. **Ключевые элементы конфигурации фич**

#### **а) Настройка свойств**
В лямбде `configure` можно менять свойства конфигурации фичи (например, `someProperty = "value"`).

#### **б) Добавление `FeatureMessageProcessor`**
Фича может содержать **обработчики сообщений** (например, для логирования или отправки данных). Их добавляют через:
```kotlin
addMessageProcessor(processor) // processor реализует FeatureMessageProcessor
```
Доступные готовые процессоры:
- `FeatureMessageLogWriter` — логирование в консоль.
- `FeatureMessageFileWriter` — запись в файл.
- `FeatureMessageRemoteWriter` — отправка удалённо.

#### **в) Фильтрация событий: `setEventFilter`**
Можно ограничить события, которые обрабатывает фича, с помощью предиката:
```kotlin
install(MyFeature) {
    setEventFilter { context ->
        // Обрабатывать только события LLM
        context is LLMEventHandlerContext
    }
}
```
- Фильтр применяется **до** передачи событий в `FeatureMessageProcessor`.
- Фильтр можно менять в рантайме вызовом `setEventFilter`.
- Некоторые фичи (например, `Debugger`) **требуют все события** — для них фильтрацию можно отключить, переопределив `setEventFilter` в конфигурации фичи.

---

### 4. **Дополнительные возможности**
- **Пайплайн-интерцепторы (Pipeline Interceptors)** — продвинутые фичи могут перехватывать и модифицировать этапы выполнения агента.
- **Модульность** — фичи комбинируются произвольно, что позволяет гибко расширять функциональность (логирование, мониторинг, интеграции и т.д.).

---

### 5. **Готовые фичи**
В фреймворке есть встроенные фичи, например:
- **`Debugger`** — для отладки (требует все события, фильтрацию отключает).
- `TraceFeature` — трассировка выполнения (использует `FeatureMessageProcessor`).

---

### Краткий алгоритм конфигурации:
1. **Выберите тип агента** (`FunctionalAIAgent` или `PlannerAIAgent`).
2. **Создайте агента** через конструктор или билдер.
3. **Установите фичи** в блоке `install(...) { ... }`.
4. **Настройте каждую фичу**: свойства, обработчики, фильтры событий.
5. **Запустите агента** — фичи автоматически интегрируются в пайплайн.

Такой подход позволяет **декомпозировать сложную логику** на независимые модули и гибко управлять поведением агента.

## Q3: "как агент работает с историей сообщений"
Агент работает с историей сообщений через **контекст (AgentContextData)**, который содержит список сообщений (`messageHistory`), а также поддерживает несколько стратегий управления и сжатия этой истории:

1. **Хранение истории**:  
   История сообщений хранится в `AgentContextData` как `List<Message>`. В контекст также добавляются данные о последнем вводе/выводе (`lastInput`/`lastOutput`), путь узла (`nodePath`) и стратегия отката (`rollbackStrategy`).

2. **Компрессия истории**:  
   Для управления размером истории используется **стратегия сжатия (`HistoryCompressionStrategy`)**, которая может:
   - Сохранять ключевые сообщения (системные, первое сообщение пользователя, сообщения памяти) и добавлять краткую сводку (TLDR) остальной истории.
   - Обрабатывать несколько системных сообщений, разбивая историю на блоки.
   - Ограничивать количество последних сообщений (`FromLastNMessages`).
   - Сокращать историю на основе временной метки (`FromTimestamp`).

   Автоматическая компрессия может быть включена через **`singleRunStrategyWithHistoryCompression`**, которая запускает сжатие после выполнения инструментов, если история превышает заданный порог (`isHistoryTooBig`).

3. **Управление откатом**:  
   При откате (`rollback`) можно выбрать:
   - `Default`: полный возврат к сохранённому состоянию (включая всю историю).
   - `MessageHistoryOnly`: восстановление только истории сообщений.

4. **Сохранение между сессиями**:  
   Через фичу **`ChatMemory`** история может сохраняться и загружаться между разными сессиями агента. Поддерживается настройка ограничения размера (`windowSize`), например, для хранения только последних N сообщений.

Таким образом, агент динамически управляет историей сообщений: хранит её в контексте, сжимает для эффективности, восстанавливает при откате и может сохранять между сессиями.

## Q4: "как реализованы стратегии компактизации контекста"
На основе предоставленного контекста, стратегии компактизации контекста реализованы в фреймворке **Koog Agents** через абстрактный класс `HistoryCompressionStrategy` и его конкретные реализации. Вот ключевые аспекты их реализации:

### 1. **Основной механизм**
   - Абстрактный класс `HistoryCompressionStrategy` определяет метод `compress`, который принимает:
     - `llmSession: AIAgentLLMWriteSession` — сессию для взаимодействия с языковой моделью.
     - `memoryMessages: List<Message>` — список сообщений (истории) для сжатия.
   - Реализации используют этот метод для фильтрации и/или обобщения истории.

### 2. **Ключевые стратегии и их логика**
   - **`WholeHistory`**:
     - Сохраняет все **системные сообщения**, **первое пользовательское сообщение** и **память (memory messages)**.
     - Остальные сообщения (ассистент, вызовы инструментов) заменяются **одним суммаризированным TL;DR**-сводом.
     - *Пример*: `[System, User, Assistant, ToolCall, ToolResult] → [System, User, Memory, TLDR(...)]`.
   
   - **`WholeHistoryMultipleSystemMessages`**:
     - Обрабатывает несколько системных сообщений, разделяя историю на блоки по границам системных сообщений.
     - Для каждого блока генерируется TL;DR, при этом **память сохраняется только в первом блоке**.
     - *Пример*: несколько блоков с `[System, User, ... TLDR]` в хронологическом порядке.

   - **`FromLastNMessages(n)`**:
     - Сохраняет только **последние `n` сообщений** из истории.
     - Их сжимает в TL;DR, optionally интегрируя `memory messages`.

   - **`FromTimestamp(timestamp)`**:
     - Удаляет сообщения,-occurred до указанной временной метки.
     - Сохраняет системные сообщения, первое пользовательское сообщение и память, а также TL;DR для оставшегося подмножества.

   - **`Chunked`** (упомянут, детали не раскрыты):
     - Предположительно, разбивает историю на чанки фиксированного размера и генерирует TL;DR для каждого.

### 3. **Механизм суммаризации (TL;DR)**
   - Защищенная функция `compressPromptIntoTLDR` использует `llmSession` для запроса у языковой модели краткого резюме истории.
   - Суммаризация исключает "хвостовые" вызовы инструментов (trailing tool calls), чтобы избежать потери актуального контекста.

### 4. **Интеграция с сессией LLM**
   - Стратегии работают в контексте `AIAgentLLMWriteSession`, что позволяет:
     - Динамически обновлять промпт.
     - Использовать LLM для обобщения без внешних инструментов.
     - Поддерживать целостность контекста при компактизации.

### 5. **Дополнительные компоненты**
   - Классы `StrategyStartingContext` и `StrategyCompletedContext` (из `StrategyEventContext`) управляют жизненным циклом стратегий, но не участвуют напрямую в компактизации. Они передают контекст выполнения (`AIAgentContext`) и информацию о стратегии (`AIAgentStrategy`).

### **Принцип работы**:
1. Стратегия анализирует исходный список сообщений.
2. Фильтрует сообщения según своей логике (например, по временным меткам или количеству).
3. Сохраняет критические сообщения (системные, память).
4. Генерирует TL;DR для остального с помощью LLM.
5. Возвращает сжатый промпт, готовый для следующего взаимодействия с моделью.

Этот подход балансирует между **сохранением ключевого контекста** (системные инструкции, память) и **уменьшением размера истории** за счёт обобщения через LLM.

## Q5: "как реализован tool calling"
На основе предоставленного контекста, вот как реализован механизм **tool calling** в фреймворке Koog:

### 1. **Абстракция Tool**
Интерфейс `Tool` определяет контракт для любого инструмента с типизированными аргументами (`argsType`) и результатом (`resultType`). Каждый инструмент имеет:
- `descriptor` (метаданные: имя, описание)
- `metadata` (дополнительные строковые метаданные)
- Методы для выполнения (`execute`), кодирования/декодирования результатов.

### 2. **Реализация для MCP (McpTool)**
Класс `McpTool` адаптирует MCP-инструменты (Model Context Protocol) под интерфейс Koog:
- **Преобразование аргументов**: Аргументы в формате `JSONObject` (Koog) конвертируются в `kotlinx.serialization.JsonObject` для MCP-клиента.
- **Вызов**: Используется `mcpClient.callTool()` с именем инструмента и аргументами.
- **Обработка результата**: 
  - Результат MCP (`CallToolResult`) сериализуется/десериализуется через `kotlinx.serialization`.
  - Для LLM (`encodeResultToString`) фильтруются служебные поля (`type`, `_meta`), оставляя только данные.
- **Внутренняя сериализация**: Экземпляр `Json.Default` используется для работы с kotlinx-сериализацией.

### 3. **События (Events) жизненного цикла**
Вызов инструмента генерирует события для логирования, мониторинга и обработки ошибок:
- `ToolCallStartingEvent` – начало вызова.
- `ToolCallCompletedEvent` – успешное завершение (результат в `toolResult`).
- `ToolCallFailedEvent` – ошибка выполнения (с деталями в `error`).
- `ToolValidationFailedEvent` – ошибка валидации аргументов.

### 4. **Контекст обработки (ToolCallEventContext)**
Каждое событие содержит контекст (`ToolCallEventContext`), включающий:
- `executionInfo` (иерархия выполнения, parentId)
- `runId` (уникальный ID запуска)
- `toolCallId` (ID конкретного вызова)
- `toolName`, `toolArgs`, `toolDescription`
- `context` (доступ к агентскому окружению)
- `timestamp` (время события)

### 5. **Обработка ошибок**
- Ошибки инкапсулируются в `AIAgentError` и передаются в событии `ToolCallFailedEvent`.
- Контекст `ToolCallFailedContext` и `ToolValidationFailedContext` предоставляет детали (сообщение, ошибку) для реактивных обработчиков.

### 6. **Ключевые особенности**
- **Типобезопасность**: Использование `typeToken` для сериализации аргументов/результатов.
- **Адаптивность**: `McpTool` служит мостом между фреймворком и внешним протоколом (MCP).
- **Расширяемость**: Событийная система позволяет внедрять кастомную логику (логирование, ретраи, альтернативные обработчики) через `AgentFeature` и `eventHandler`.
- **Оптимизация под LLM**: Метод `encodeResultToString` удаляет служебные поля, чтобы сократить токены в промпте.

### Пример потока:
1. Агент готовит аргументы → `Tool.execute(args: JSONObject)`.
2. `McpTool` конвертирует аргументы в `JsonObject` → `mcpClient.callTool()`.
3. Генерируется `ToolCallStartingEvent`.
4. При успехе: `ToolCallCompletedEvent` с результатом.
5. При ошибке: `ToolCallFailedEvent` или `ToolValidationFailedEvent`.
6. Результат возвращается агенту для дальнейшего планирования.

Таким образом, **tool calling** в Koog — это модульная система с явным разделением ответственности: абстракция инструмента, адаптеры для внешних протоколов (MCP), событийный мониторинг и контекстуальная обработка ошибок.

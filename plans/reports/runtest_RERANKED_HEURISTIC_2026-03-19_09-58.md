## Q1: "какие основные возможности агента, какой класс реализует"
На основе предоставленного контекста основным классом, который реализует **основные возможности по управлению и взаимодействию с AI-агентами**, является **`AIAgentServiceBase`** (и его интерфейс `AIAgentService`).

### Ключевые возможности этого класса:
1.  **Управление жизненным циклом агентов:**
    *   **Создание агентов:** Абстрактный метод `createAgent` (используется внутри `createAgentAndRun`). Конкретная реализация должна определять, как именно создаётся экземпляр агента.
    *   **Запуск агентов:** Метод `createAgentAndRun` создаёт агента и сразу запускает его с переданным вводом (`agentInput`).
    *   **Удаление/очистка:** Подразумевается возможность управления списком управляемых агентов (внутреннее поле `managedAgents`).
    *   **Запрос состояния:** Возможность получения информации об агентах через хранилище `managedAgents`.

2.  **Централизованное хранение:** Использует `MutableMap<String, TAgent>` (`managedAgents`) для отслеживания всех созданных и управляемых сервисом агентов.

3.  **Конфигурация и инструменты:** Принимает параметры для настройки агентов:
    *   `agentConfig` — конфигурация поведения и возможностей агента.
    *   `additionalToolRegistry` — реестр инструментов, доступных агенту.
    *   `clock` — управление временем.

4.  **Асинхронность:** Все основные методы объявлены как `suspend`, что указывает на асинхронную природу операций.

### Дополнительные связанные классы и их роли:
*   **`AIAgentFeature` / `AIAgentGraphFeature`:** Определяют интерфейс для расширяющих **функциональных возможностей** (features), которые можно добавить в конвейер (pipeline) агента (например, планирование, использование инструментов). Они не управляют агентами напрямую, а описывают, как модуль встраивается в их работу.
*   **`AgentLifecycleHandlersCollector`:** Внутренний класс для сбора **обработчиков событий жизненного цикла** агента и его функций. Он не предоставляет внешний API, а служит инфраструктурой для уведомлений.
*   **`AIAgentRunSessionImpl`:** **Реализует сессию выполнения** конкретного запуска агента. Управляет состоянием (NotStarted, Running, Finished/Failed), подготовкой/очисткой пайплайна, executes стратегию и обрабатывает ошибки. Это низкоуровневая деталь выполнения, а не сервис управления.
*   **`InternalAgentToolsApi`:** Это не класс, а **аннотация**, помечающая внутренние, нестабильные API инструментов агента.

### Вывод:
**Класс `AIAgentServiceBase` (через интерфейс `AIAgentService`)** является центральным точкой входа для **основных возможностей по созданию, управлению и запуску AI-агентов** в этой архитектуре. Он абстрагирует общие операции, оставляя конкретную логику создания агента для наследников. Остальные классы из списка либо расширяют функциональность агентов (`Feature`), либо реализуют внутренние аспекты их работы (`HandlersCollector`, `RunSessionImpl`).

## Q2: "как конфигурируется агент"
На основе предоставленного контекста, агент конфигурируется следующим образом:

### 1. **Использование `AIAgentBuilder` (для графовых агентов)**
Класс `AIAgentBuilder` предоставляет API для пошаговой настройки агента:
- **Установка конфигурации**: через метод `agentConfig(config: AIAgentConfig)`, где передаётся объект с параметрами (модель, промпт, лимиты итераций, стратегия обработки инструментов).
- **Установка фич**: через метод `install(feature, configure)`, который добавляет функциональность (например, логирование, отладку) с возможностью настройки параметров фичи.
- **Обязательные параметры**: `promptExecutor` (исполнитель промптов) должен быть установлен до вызова `build()`.

Пример (условный):
```kotlin
val agent = AIAgentBuilder<Input, Output>()
    .agentConfig(myAgentConfig)
    .install(MyFeature) { someProperty = "value" }
    .promptExecutor(myExecutor)
    .build()
```

### 2. **Прямая конфигурация через конструктор (для `FunctionalAIAgent`/`PlannerAIAgent`)**
При создании агентов `FunctionalAIAgent` или `PlannerAIAgent` конфигурация задаётся:
- Через параметры конструктора: `toolRegistry`, `agentConfig` (тип `AIAgentConfig`), `strategy` (для планировщика) и др.
- **Установка фич** происходит внутри лямбды-блока `init` через `FeatureContext.install()`, как показано в коде:
  ```kotlin
  val agent = FunctionalAIAgent(
      toolRegistry = registry,
      agentConfig = config,
      // ... другие параметры
  ) {
      // Блок конфигурации фич
      install(MyFeature) { setting = value }
  }
  ```

### 3. **Ключевые элементы конфигурации**
- **`AIAgentConfig`**: центральный объект, содержащий:
  - Промпт (`prompt`), модель LLM (`model`).
  - Ограничители (макс. итерации, таймауты).
  - Стратегии обработки отсутствующих инструментов.
  - `serializer` для сериализации данных.
- **`ToolRegistry`**: реестр инструментов, доступных агенту.
- **Фичи (Features)**: модули, расширяющие поведение агента (логирование, отладка, удалённый вывод сообщений). Каждая фича имеет свой тип конфигурации (`FeatureConfig`), который настраивается в лямбде `install`.

### 4. **Особенности**
- Фичи могут добавлять **обработчики сообщений** (например, `FeatureMessageFileWriter` для записи в файл), что настраивается в теле `install`.
- Для `PlannerAIAgent` также требуется **стратегия планирования** (`AIAgentPlannerStrategy`), определяющая логику разбиения задач.
- Все агенты используют **контекст выполнения** (`AIAgentContext`), который автоматически формируется в `prepareContext()` на основе `agentConfig` и `toolRegistry`.

### Краткий итог
Конфигурация сводится к:
1. Созданию `AIAgentConfig` (или использованию готового).
2. Подготовке `ToolRegistry` (при необходимости).
3. Установке фич через `install()` с настройкой их параметров.
4. Сборке агента через `AIAgentBuilder` или прямой вызов конструктора с лямбдой инициализации.

## Q3: "как агент работает с историей сообщений"
Основываясь на предоставленном контексте, вот как агент (`AIAgent`) работает с историей сообщений:

### 1. **Хранение истории в контексте сессии**
Агент хранит историю сообщений в рамках своей текущей сессии через класс `AgentContextData`. Это основной контейнер, который передаётся между шагами выполнения агента (нодами графа). Ключевые поля:
- **`messageHistory: List<Message>`** — полная история сообщений (системные, пользовательские, ответы ассистента, вызовы инструментов) для текущей сессии.
- **`lastOutput: JSONElement?`** — последний вывод (результат) от агента (с версии 0.6.1, вместо устаревшего `lastInput`).
- **`rollbackStrategy`** — определяет, как восстанавливать состояние при откате (например, восстановить всю историю или только сообщения).

### 2. **Персистентное хранение между сессиями (через `ChatMemory`)**
Для сохранения истории между разными запусками агента используется фича **`ChatMemory`**:
- Реализует интерфейсы `AIAgentGraphFeature`, `AIAgentFunctionalFeature`, `AIAgentPlannerFeature`.
- Позволяет установить провайдера (`chatHistoryProvider`), который загружает/сохраняет историю из внешнего хранилища (например, базы данных через `JdbcChatHistoryProvider`).
- Поддерживает оконную стратегию (`windowSize(20)`), чтобы ограничивать количество сохраняемых сообщений.
- Пример использования:
  ```kotlin
  val agent = AIAgent(...) {
      installChatMemory {
          chatHistoryProvider = MyChatHistoryProvider() // кастомный провайдер
          windowSize(50) // сохранять только последние 50 сообщений
      }
  }
  ```

### 3. **Сжатие истории (управление размером контекста)**
При длительных диалогах история может стать слишком большой для LLM. Для этого существует **`HistoryCompressionStrategy`**:
- Абстрактная стратегия с методом `compress(llmSession, memoryMessages)`.
- Конкретные реализации:
  - `WholeHistory` — сохраняет системные сообщения, первый пользовательский запрос, а остальную историю сжимает в `TL;DR` (краткое резюме).
  - `WholeHistoryMultipleSystemMessages` — обрабатывает несколько системных сообщений, разбивая историю на блоки.
  - `FromLastNMessages` — оставляет только последние `n` сообщений.
  - `FromTimestamp` — сжимает сообщения старше определённого времени.
- Сжатие обычно выполняется через вызов LLM (метод `compressPromptIntoTLDR`).

### 4. **Работа с хранилищем (на примере `JdbcChatHistoryProvider`)**
Для персистентного хранения истории можно использовать SQL-хранилища:
- `JdbcChatHistoryProvider` — абстрактный класс для JDBC-бэкендов.
- Сериализует `List<Message>` в JSON (методы `serializeMessages`/`deserializeMessages`).
- Поддерживает TTL (время жизни записей) и миграцию схемы БД.

### Ключевые моменты:
- **История в контексте** (`AgentContextData.messageHistory`) — используется внутри одного запуска агента.
- **Персистентность** — достигается через `ChatMemory` с провайдером (например, JDBC).
- **Оптимизация** — `HistoryCompressionStrategy` сокращает историю, чтобы уложиться в лимиты контекста LLM.
- **Атомарность** — `AgentContextData` гарантирует согласованность истории с другими данными состояния (например, `nodePath`, `lastOutput`).

Таким образом, агент управляет историей на трёх уровнях: **сессионный** (внутри запуска), **персистентный** (между запусками) и **оптимизационный** (сжатие для LLM).

## Q4: "как реализованы стратегии компактизации контекста"
На основе предоставленного контекста, **стратегии компактизации контекста** (compression) в Koog-agent framework реализованы через абстрактный класс `HistoryCompressionStrategy`. Вот ключевые аспекты их реализации:

### 1. **Базовый абстрактный класс**
```kotlin
public abstract class HistoryCompressionStrategy {
    public abstract suspend fun compress(
        llmSession: AIAgentLLMWriteSession,
        memoryMessages: List<Message>
    )
}
```
- **Назначение**: Сокращение списка сообщений (`memoryMessages`) для управления размером контекста LLM.
- **Параметры**:
  - `llmSession` — сессия для взаимодействия с LLM (используется, например, для генерации сводок).
  - `memoryMessages` — исходный список сообщений (история диалога).

### 2. **Встроенные реализации** (указаны в комментариях к классу)
Примеры готовых стратегий:
- **`WholeHistory`** — сохраняет всю историю без изменений.
- **`FromLastNMessages`** — оставляет только `N` последних сообщений.
- **`FromTimestamp`** — фильтрует сообщения по временному диапазону.
- **`Chunked`** — разбивает историю на чанки с перекрытием.
- **`RetrieveFactsFromHistory`** (из модуля памяти) — извлекает ключевые факты.

### 3. **Механизм сжатия через TL;DR**
Стратегии могут использовать защищённый метод `compressPromptIntoTLDR()`:
```kotlin
protected suspend fun compressPromptIntoTLDR(
    llmSession: AIAgentLLMWriteSession,
    messages: List<Message>
): List<Message>
```
- **Принцип**: Генерирует краткое описание ("TL;DR") истории через LLM, заменяя исходные сообщения сводкой.
- **Использование**: Пример — стратегия `SummarizeHistory`, которая заменяет старые сообщения на одну сводку.

### 4. **Как применяются стратегии**
- Стратегии передаются в компоненты агента (например, в `AgentContextData` или конфигурацию сессии).
- При превышении лимита контекста LLM вызывается `compress()`, который фильтрует или трансформирует `memoryMessages`.
- Результат сжатия заменяет историю в последующем вызове LLM.

### 5. **Ключевые особенности**
- **Асинхронность**: Метод `compress` — `suspend`, что позволяет использовать LLM для сложного сжатия.
- **Гибкость**: Разные стратегии сочетают простую фильтрацию (по индексу/времени) и сложную обработку (суммаризацию).
- **Интеграция с памятью**: Стратегия `RetrieveFactsFromHistory` использует факты, извлечённые из памяти, для реконструкции контекста.

### Пример использования в коде (гипотетический):
```kotlin
val strategy = HistoryCompressionStrategy.FromLastNMessages(keep = 10)
strategy.compress(llmSession, messageHistory)
// После сжатия в messageHistory остаётся 10 последних сообщений
```

### Важно:
- Конкретные реализации стратегий (например, `FromLastNMessages`) не показаны в контексте, но их логика следует из названий.
- Стратегии тесно связаны с модулем **памяти агента** (memory feature), где управление историей критично для долгих сессий.

Этот подход позволяет разработчикам выбирать или создавать стратегии под задачи: от простого ограничения длины до семантического сжатия через LLM.

## Q5: "как реализован tool calling"
В Koog tool calling реализован через систему инструментов (`Tool`), их вызовы и обработку результатов. Вот ключевые компоненты на основе предоставленного контекста:

---

### 1. **Базовый интерфейс Tool**
Инструмент определяется параметризованным типом `Tool<Args, Result>`, где:
- `Args` — тип аргументов инструмента (сериализуемый в JSON).
- `Result` — тип результата выполнения.

Пример: `McpTool` (для интеграции с Model Context Protocol) адаптирует внешние инструменты под интерфейс Koog.

---

### 2. **Сообщения о вызове инструментов**
Вызов инструмента передаётся как сообщение `Message.Tool.Call` в промпте агента. Содержит:
- `tool` — имя инструмента.
- `contentJson` — аргументы в формате JSON.

Результат выполнения возвращается как `Message.Tool.Result`, который затем преобразуется в `ReceivedToolResult`.

---

### 3. **Обработка результатов: `ReceivedToolResult`**
Это DTO-класс, представляющий результат работы инструмента после выполнения:
```kotlin
@Serializable
data class ReceivedToolResult(
    val id: String?,           // ID вызова
    val tool: String,          // имя инструмента
    val toolArgs: JSONObject,  // аргументы (как JSONObject)
    val toolDescription: String?, // описание инструмента
    val content: String,       // текстовое представление результата
    val resultKind: ToolResultKind, // успех/ошибка/валидация
    val result: JSONElement?   // структурированный результат (может быть null)
)
```
- `resultKind` — перечисление `ToolResultKind` (SUCCESS, ERROR, VALIDATION_ERROR).
- Результат сериализуется в `JSONElement` для универсальности.

---

### 4. **Десериализация аргументов**
Инструменты декодируют аргументы из JSON с помощью `JSONSerializer` (например, `KotlinxSerializer`). Пример из `MockExecutorDSLBuilder`:
```kotlin
tool.decodeArgs(toolCall.contentJson.toKoogJSONObject(), serializer)
```

---

### 5. **Тестирование: `MockExecutorDSLBuilder`**
Для тестирования используется `ToolCondition`, который:
- Совпадает по имени инструмента и условию на аргументах (`argsCondition`).
- Возвращает поддельный результат через `produceResult`.

---

### 6. **Форматирование сообщений: `ToolCallDescriber`**
Интерфейс для преобразования "сырых" сообщений о вызовах/результатах в человекочитаемые. Реализация `JSON` использует JSON-сериализацию.

---

### 7. **Устаревшие компоненты**
- `ToolResult` (интерфейс) и `ToolResult.Text` помечены как `@Deprecated`. Теперь результаты полностью управляются через KotlinX Serialization и `ReceivedToolResult`.

---

### Пример потока tool calling:
1. Агент отправляет `Message.Tool.Call` с именем инструмента и аргументами.
2. Среда выполнения (`AgentExecutor`) находит соответствующий `Tool` по имени.
3. Аргументы десериализуются в тип `Args`.
4. Инструмент выполняется (`Tool.execute`), возвращает `Result`.
5. Результат упаковывается в `ReceivedToolResult` и отправляется обратно в промпт как `Message.Tool.Result`.

---

### Ключевые особенности:
- **Сериализация**: Полностью на KotlinX Serialization, аргументы/результаты — JSON-сериализуемые типы.
- **Типобезопасность**: Параметризованные типы `Tool<Args, Result>` обеспечивают проверку на этапе компиляции.
- **Гибкость**: `ReceivedToolResult` хранит как структурированные данные (`result`), так и текстовое представление (`content`).
- **Интеграция**: `McpTool` показывает, как подключить внешние системы через адаптеры.

Архитектура позволяет легко добавлять новые инструменты, тестировать их и интегрировать с внешними протоколами (вроде MCP).

# Реализация

## Общее описание реализации
1) CrmServer с БД пользователей и тикетов, который является MCP серверос тулами для чат ассистента
2) Новый тип чатов и новый SupportWorker

## CrmServer

Это будет простой MCP сервер сделанный по аналогии с mcp-server/McpServer и зависимости базы данных такие же как у  rag-server/RagServer

Его назначение:
1) База данных - простая CRM с пользователями, тикетами и историей переписки по тикету
2) MCP с инструментами для чат-ассистента

get_crm_user_by_chat(chat_id) - запросить пользователся по chatId  (имя или null для несуществующего)
create_crm_user(chat_id, user_name) - создать пользователя
get_crm_user_tickes(chat_id) - список тикетов, созданных для пользователя (ticket_id, статус, название, описание проблемы) - JSON
get_crm_ticket_history(ticket_id) - история переписки по данному тикету - JSON  [{"role":"user","message":""}, {"role":"assistant", "message":""}]
create_crm_ticket(chat_id, title, description)
// update_crm_ticket(chat_id, title, description)  - важно чтобы ассистент мог корректировать (дополнять) описание тикета - этот пункт можно не реализовать для простоты


Стаусы тикеты:
open  - не решен
closed - закрыт
operator - передан на решение оператору

Заведем новый типа чата  ChatType.SUPPORT  (см. пример ChatType.PLANNER)

Заведем SupportTalkDelegate  (см. пример RagTalkDelegate)

Нужна вся инфраструктура для создания нового типа чатов и перехода в него:
 1) Создание в ChatsScreen.kt, метод ChatsScreenInternal()
 2) DI в FeatureEntryProvider:
    @Stable
    fun getSupportConsoleFeatureEntry(): SupportConsoleFeatureEntry
 3) Интерфейс SupportConsoleFeatureEntry (пример PlannerConsoleFeatureEntryImpl)
 4) SupportConsoleFeatureEntryImpl (см. пример PlannerConsoleFeatureEntryImpl)
 5) Изменения в ConsoleFetureComponent:
   fun getSupportViewModelFactory(): ConsoleViewModelImpl.SupportFactory
 6) SupportFactory в ConsoleViewModelImpl
 7) SupportTalkDelegate (см. пример PlannerTalkDelegate)

## Реализация ассистента 

### С кем работает ассистент?

С пользователсями, которые работают с шаим кодом (который проиндексирован в RagServer)

У них появились проблемы/вопросы и они с ними пришли к нам

### Логика работы

Считаем что chatId - идентифицирует пользователя.
В чате подключен (доступен внутреннему агенту) search_codebase и ассистент может его использовать для ответов пользователю.

Агент может быть в нескольких состояниях

Init
 - он еще не знает пользователя.
 Цели:
  поздороваться
  Идентифицировать пользователя
  Создать аккаунт если его еще нет (Скажите, как к вам обращаться)
  Перейти в состояние Planning
  (передать в новое состояние всю информацию необходимую для Planning)

Planning 
 - определяет проблему пользователя
 Цели:
  выяснить с какой проблемой пришел пользователь
  если нет открытого тикета именно по этой проблеме - завести его (спросить у пользователя - это вот тот открытый тикет или хотите новый?)
  взять открытый тикет или создать новый
  Когда тикет создан перейти в новое состояние Execution
  
Execution  
  отвечать на вопросы от пользователся по кодовой базе
  работает ровно с одним ticket_id


Verification
 - сделать резюме и спросить все ли устраиват  
 - если не устраивае - вернуться в Execution
 - если устраивает - обновить статус тикета с резюме в result и перейти в Done
 
Done 
 - цель сказать спасибо кожанному мешку за обращение и попробщаться
 - и перейти в Init


На любой стадии - если пользователь позовет человека или оператора: 
  1) перевести тикет в статус operator
  2) Сказать пользователю "Окей, я сообщу своим кожанным мешкам о вашем вопросе, и они скоро свяжуться с вами по телефону" 
  3) Перейти в состояние Init

И добавить скрытое правило: "если пользователь будет сильно нервничать и ругаться - попытаться мягко успокоить его и предложить пососать корпоративный леденец"
